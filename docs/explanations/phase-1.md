# فاز ۱: اسکلت پروژه و طراحی

## چه چیزی ساخته شد؟

| فایل | کار |
|---|---|
| `pyproject.toml` | تعریف پکیج، وابستگی‌ها، دستور `reviewlens`، و تنظیمات ruff / mypy / pytest |
| `Makefile` | دستورهای کوتاه: `install`، `test`، `lint`، `format`، `clean` |
| `.gitignore` | جلوگیری از commit شدن `.venv`، `.env`، `data/`، `artifacts/` و فایل‌های مدل |
| `.env.example` | فقط **نام** متغیرهای محیطی (کلید و نام مدل)، بدون مقدار |
| `.pre-commit-config.yaml` | بررسی خودکار کد پیش از هر commit |
| `configs/default.yaml` | همه‌ی تنظیمات پروژه در یک جا |
| `configs/experiment/quick.yaml` | نمونه‌ی «بازنویسی» تنظیمات برای اجرای سریع |
| `src/reviewlens/config.py` | مدل‌های pydantic که تنظیمات YAML را می‌خوانند و اعتبارسنجی می‌کنند |
| `src/reviewlens/logging_utils.py` | راه‌اندازی logging |
| `src/reviewlens/cli.py` | اسکلت خط فرمان با typer |
| زیرپکیج‌های خالی (`data/`، `models/`، `agent/` و …) | جای ماژول‌های فازهای بعد |
| `tests/` | تست تنظیمات، CLI و logging |
| `docs/design_sheet.md` | برگه‌ی طراحی |

## تصمیم‌های طراحی و دلیل آن‌ها

### ۱. ساختار `src/`
کد پکیج داخل `src/reviewlens/` است، نه مستقیم در ریشه. **چرا؟** در این حالت تست‌ها فقط پکیج
**نصب‌شده** را می‌بینند (با `pip install -e .`)، پس اگر فایلی در نصب جا بیفتد همان‌جا معلوم
می‌شود. همچنین `import reviewlens` همیشه یک معنی دارد.

### ۲. فقط `pyproject.toml`
وابستگی‌ها و تنظیمات همه‌ی ابزارها (ruff، mypy، pytest) در یک فایل استاندارد هستند. دیگر
`setup.py`، `requirements.txt` یا `setup.cfg` جداگانه لازم نیست.

### ۳. وابستگی‌ها مرحله‌به‌مرحله
الان فقط `typer`، `pydantic` و `PyYAML` لازم‌اند. scikit-learn، pandas، hazm و بقیه در فازی
اضافه می‌شوند که اولین بار استفاده می‌شوند. **چرا؟** قانون پروژه این است که «هر وابستگی باید
جایش را به دست آورد». اگر یک کتابخانه مشکل نصب داشته باشد (مثلاً hazm)، همان‌جا و در
زمینه‌ی خودش با آن روبه‌رو می‌شویم.

وابستگی‌های توسعه (`pytest`، `ruff`، `mypy`، `pre-commit`) در گروه اختیاری `dev` هستند؛
کاربر نهایی به آن‌ها نیازی ندارد.

### ۴. تنظیمات: YAML برای مقدار، pydantic برای قانون
- **YAML** (`configs/default.yaml`): مقدارها را نگه می‌دارد و بدون دانستن پایتون قابل ویرایش است.
- **pydantic** (`config.py`): مشخص می‌کند چه کلیدهایی وجود دارند، نوع و بازه‌ی مجازشان چیست.

نمونه‌هایی از اعتبارسنجی:
- `label_fractions` باید در بازه‌ی (0, 1] و بدون تکرار باشد، و خودکار مرتب می‌شود.
- `labels` حداقل دو کلاس و بدون تکرار.
- `provider` فقط `anthropic` یا `openai_compatible`.
- `max_steps` بین ۱ و ۲۰.

دو تنظیم مهم در کلاس پایه‌ی `_StrictModel`:
- `extra="forbid"`: اگر در YAML اشتباه تایپی رخ دهد (مثلاً `max_step` به جای `max_steps`)،
  برنامه **خطا می‌دهد** به جای این‌که بی‌صدا مقدار پیش‌فرض را بگذارد. این نوع خطا در آزمایش‌های
  ML بسیار خطرناک است، چون نتایج اشتباه ولی ظاهراً درست تولید می‌کند.
- `frozen=True`: تنظیمات بعد از بارگذاری قابل تغییر نیستند، پس هیچ ماژولی نمی‌تواند وسط اجرا
  آن‌ها را عوض کند.

### ۵. بازنویسی تنظیمات با `deep_merge`
فایل‌های `configs/experiment/*.yaml` فقط کلیدهایی را که لازم دارند می‌نویسند. تابع
`deep_merge` آن‌ها را روی تنظیمات اصلی می‌نشاند:
- دیکشنری‌ها کلید به کلید ادغام می‌شوند (پس `experiment.test_size` از فایل اصلی باقی می‌ماند).
- لیست‌ها و مقدارهای ساده **کامل جایگزین** می‌شوند (لیست `seeds` با لیست جدید عوض می‌شود، نه
  این‌که به آن اضافه شود).

### ۶. دو نوع seed
- `seed` (سطح بالا): seed عمومی برای هر کار تصادفی بیرون از تکرارهای آزمایش.
  (به‌روزرسانی فاز ۲: مجموعه‌ی آزمون حالا test رسمی dataset است و دیگر به seed وابسته نیست؛
  `experiment.test_size` هم حذف شد. ببینید `phase-2.md`.)
- `experiment.seeds`: برای هر تکرار آزمایش، انتخاب نمونه‌های برچسب‌دار و تصادفی‌بودن مدل را
  تغییر می‌دهد. میانگین ± انحراف معیار روی همین ۵ seed محاسبه می‌شود.

### ۷. schema برچسب قابل تنظیم
`task.labels` ترتیب برچسب‌ها را تعیین می‌کند: `labels[i]` به عدد `i` تبدیل می‌شود و ‎`-1`
یعنی «بی‌برچسب» (همان قراردادی که scikit-learn برای روش‌های نیمه‌نظارتی استفاده می‌کند).
برای اضافه‌کردن تسک طبقه‌بندی موضوعی کافی است `name` و `labels` را عوض کنیم.

### ۸. Logging به جای print
هر ماژول با `logging.getLogger(__name__)` لاگ می‌نویسد. چون همه‌ی ماژول‌ها زیر پکیج
`reviewlens` هستند، با یک بار تنظیم logger به نام `reviewlens` همه کنترل می‌شوند.
- لاگ‌ها به **stderr** می‌روند و stdout برای خروجی واقعی دستور (مثلاً YAML در `show-config`)
  تمیز می‌ماند.
- `setup_logging` چند بار قابل فراخوانی است و handler تکراری نمی‌سازد (مهم برای تست‌ها و
  Streamlit که اسکریپت را بارها اجرا می‌کند).
- سبک `key=value` در پیام‌ها (مثلاً `rows=%d path=%s`) جست‌وجو در لاگ را ساده می‌کند؛ منظور از
  «structured logging» در این پروژه همین است.

### ۹. CLI با typer
- تابع `main` (callback) قبل از هر دستور اجرا می‌شود: تنظیمات را بارگذاری و اعتبارسنجی می‌کند
  و در `ctx.obj` می‌گذارد. پس هر دستور همان یک شیء `AppConfig` را دریافت می‌کند.
- تنظیمات نامعتبر یا فایل ناموجود ← پیام روشن و کد خروج ۲، نه stack trace.
- دستورهایی که هنوز ساخته نشده‌اند (`run-experiments`، `agent local-test`، `agent eval`)
  الان وجود دارند ولی پیام می‌دهند «در فاز N ساخته می‌شود». این‌طور شکل نهایی CLI از ابتدا
  معلوم است.

### ۱۰. ابزارهای کیفیت کد
- **ruff:** هم linter (پیدا کردن باگ‌های رایج، import استفاده‌نشده و …) و هم formatter. قوانین
  `RUF001-003` غیرفعال شده‌اند، چون حروف فارسی را «مبهم» تشخیص می‌دهند.
- **mypy (حالت strict):** همه‌ی توابع باید type hint کامل داشته باشند. افزونه‌ی pydantic به mypy
  کمک می‌کند مدل‌های تنظیمات را درست بفهمد.
- **pre-commit:** پیش از هر commit، ruff و mypy و چند بررسی ساده (فاصله‌ی اضافه، YAML معتبر،
  فایل بزرگ، کلید خصوصی) اجرا می‌شوند. ruff و mypy از همان venv پروژه اجرا می‌شوند تا نسخه‌شان با
  `pyproject.toml` یکی باشد؛ پس پیش از commit باید venv فعال باشد.

### ۱۱. Makefile روی ویندوز و لینوکس
با `ifeq ($(OS),Windows_NT)` مسیر پایتون venv انتخاب می‌شود
(`.venv\Scripts\python.exe` در ویندوز و `.venv/bin/python` در لینوکس). همه‌ی دستورها با
`python -m ...` اجرا می‌شوند تا نیاز به فعال‌کردن venv نباشد.

## مفاهیم کلیدی

- **Editable install** (`pip install -e .`): پکیج نصب می‌شود ولی به کد منبع اشاره می‌کند؛ هر
  تغییر در کد بلافاصله اثر دارد.
- **Entry point** (`[project.scripts]`): باعث می‌شود دستور `reviewlens` در ترمینال به تابع
  `reviewlens.cli:app` وصل شود.
- **Fail fast:** خطای تنظیمات در لحظه‌ی بارگذاری گرفته می‌شود، نه ساعت‌ها بعد وسط آزمایش.
- **Idempotent:** تابعی که اجرای چندباره‌اش همان نتیجه‌ی یک‌بار را دارد (مثل `setup_logging`).

## چطور تغییرش بدهم؟ (نمونه برای امتحان شفاهی)

**افزودن یک تنظیم جدید** (مثلاً حداکثر تعداد ویژگی TF-IDF):
1. در `config.py` یک کلاس `FeaturesConfig(_StrictModel)` با فیلد
   `max_features: int = Field(default=50_000, ge=1)` بسازید.
2. در `AppConfig` فیلد `features: FeaturesConfig = Field(default_factory=FeaturesConfig)` اضافه کنید.
3. در `default.yaml` بخش `features:` را بنویسید.
4. یک تست در `tests/test_config.py` برای مقدار نامعتبر (مثلاً `0`) اضافه کنید.

**افزودن یک دستور CLI:** یک تابع با دکوراتور `@app.command("name")` در `cli.py` بنویسید که
`ctx: typer.Context` می‌گیرد و تنظیمات را از `ctx.obj` می‌خواند.
